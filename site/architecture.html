How keel is built

Each layer is the smallest thing that works end to end; the interest is in the layers and the boundaries between them. Real robots are in scope: control, fieldbuses and microcontrollers are built on top, as crates of their own.

processestwo planes

A coordinator, a daemon per machine, a process per node

The data plane

Messages between nodes. On a machine they go node to node through shared memory, and the daemon never touches them; between machines, daemon to daemon over TCP. It has to be fast.

The control plane

Registration, lifecycle, deployment, and the state and metrics the tools show. It can be slow and simple: JSON lines, over a Unix socket on a machine and TCP between them. The CLI, the TUI, the coordinator and deployment all speak only this.

On one machine

keel run is then both the coordinator and the only daemon, in one process. The daemon is a small init for its nodes: process groups, PR_SET_PDEATHSIG, ordered stop, restarts.

shared memorythree small files

A message on one machine

Everything a hop needs lives in files in the session's directory in /dev/shm, created by the daemon before the nodes start and mapped by each node. Byte by byte:

  1. The sender takes a free region of its pool, one whose count is 0 (growing it if the payload is bigger), and writes the payload in place. A node has at most 32 regions: that bounds how many of its messages can be in flight.
  2. It fills the header: its span, the trace it belongs to, the message it was handling (its parent), when it was published, and the stamp, inherited from that parent unless the sender sets it. The reference count becomes the number of receivers, before any of them can see it.
  3. For each receiver, it puts the descriptor in the channel (with keep: latest, it swaps the mailbox and releases what it displaced), then bumps the receiver's bell.
  4. The receiver reads its bell, looks through its channels in turn, maps the region on first use and records the hop's latency. It sleeps on the bell's futex, spins on it, or spins only around when its inputs are due.
  5. Dropping the sample decrements the count. At 0 the sender can write there again, so a reader never sees a payload change under it.

The daemon creates these files, spawns the nodes and watches them, and isn't on this path at all (decisions 0005, 0015). Tracing adds a clock read and a few atomic adds per message on each side, into per-node files the daemon reads.

Across machines

A node sending to another machine doesn't know it: its output's route ends in a channel its daemon reads. The receiving daemon copies the payload into a region of its own and delivers it like a local message. One connection per direction and machine pair keeps a node's messages in order. Offsets are known to a few milliseconds over Wi-Fi: phases hold within a machine, not across (decisions 0013, 0014).

keel-controla layer above keel

Control: the dataflow is the hardware interface

Cycles

A bus master or simulation publishes its state and waits, up to a deadline, for the command that answers it (recognised by its trace parent), then applies it before the tick ends. --cycle next takes it at the next tick instead; --cycle lockstep steps a simulation when the answer comes.

Stamps

A state is stamped when its joints were read, or with the simulation's time; a command inherits its state's stamp. Controllers take their time steps from stamps, so real time, replay and lockstep look the same to them.

Phases

Periodic loops tick on multiples of their period on the machine's clock, so two arms' masters are in phase whenever they started; phase_us moves a node along its period. A node can spin only around when its inputs are due.

The numbers are on the timing page; the details in docs/control.md and decisions 0021, 0027 to 0029.

by hashbuild once, ship what's missing

Deployment

  • History and rollback: each deployment is recorded; keel rollback switches back, keel update brings new code into a running dataflow node by node.
  • Branches: a deployed dataflow has named branches, to try something without losing what works; keel diff compares them node by node.
  • Fleets: each robot is a deployment of its own; keel fleet update --only robot-3 tries new code on one robot first.
  • Machines: keel provision installs keel over SSH as a systemd service with real-time limits and a shared token; keel image builds a 4.5 MB initramfs where keel is process 1.
